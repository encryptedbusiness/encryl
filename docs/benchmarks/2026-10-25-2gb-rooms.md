# 1 CPU / 2 GiB room benchmark

Date: 2026-10-25
Commit: working tree on `v2`
Host: `lima-encryl-dev`, Apple Silicon, VM 8 vCPU / 15.6 GiB
Kernel: 6.8.0-147-generic
Memory budget: server cgroup `MemoryMax=2G`, `CPUQuota=100%`
Go: 1.27.2 linux/arm64
Client: tcpkali 1.2.0 for 500k density; no 500k Go client
Command: see each section
TLS mode: plaintext `ws://`
Raw: console output and journal in this report

## Why 2 GiB

The 1-GiB run is retained in `2026-10-25-1c1g-rooms.md`. It OOM-killed the
server at 500k room memberships because Linux kernel socket slab is about
3.6 KiB per live TCP connection. The server process itself was under 1 GiB;
the cgroup total was not. The active benchmark and gate budget is now **2 GiB**.

## 500k connections, 5000 rooms x 100 members

Server:

```sh
/tmp/encryl-fanout -addr 127.0.0.1:18092 -max-conns 500000 \
  -rooms 5000 -room-size 100 -loops 1 \
  -count 1000 -interval 10ms -auto-start=false
```

under:

```sh
systemd-run --scope -p CPUQuota=100% -p MemoryMax=2G -p MemorySwapMax=0 ...
```

Client:

```sh
tcpkali --ws -c 500000 --connect-rate 10000 -T 90 \
  -H 'Sec-WebSocket-Protocol: encryl.v2' ...
```

## Changes that made the 2-GiB run stable

- Room membership uses compact per-connection slices; the old map-per-connection
  cost 17.0 MiB per 100k and now uses 10.0 MiB.
- Production `room.NewSized` uses a lazy dense per-slot table.
- Room names are canonicalized to one string per room.
- `bench/workload` reports p99.9/p99.99; `bench/fanout` supports rooms, room
  size, one loop, and p99.99.
- The workload server no longer reserves 2x the connection ceiling.
- tcpkali replaces the Go client for 500k density, removing the ~10.9 GiB
  client-side allocation observed in the earlier run.


## Hub sharding result

The room directory now has **4 xsync hub shards**, selected by FNV-1a over the
room name, matching the v1/uring `NumCPU*4` shape for this one-CPU host.

Same 500k / 5000-room benchmark:

| Metric | Before hubs | After hubs | Change |
| ------ | -----------: | ---------: | -----: |
| p50 | 2.195 ms | **2.185 ms** | flat |
| p95 | 3.257 ms | **2.376 ms** | ~27% better |
| p99 | 4.354 ms | **3.514 ms** | ~19% better |
| p99.9 | 5.904 ms | **5.181 ms** | ~12% better |
| p99.99 | 5.904 ms | **5.181 ms** | ~12% better |
| Max | 7.345 ms | **5.473 ms** | ~25% better |
| Process RSS | 448 MiB | **431 MiB** | -17 MiB |
| cgroup peak | 1.20 GiB | **1.18 GiB** | -20 MiB |

### Maximum connections at 2 GiB

| Variant | Pass | OOM |
| ------- | ---: | --: |
| Before hubs | **850,000** | 860,000 |
| 4 hubs | **800,000** | 850,000 |

At 800k with hubs: process RSS **720 MiB**, cgroup peak **1.93 GiB**, zero
protocol/file-table errors. The hub version improves read/write latency but
costs enough room-metadata memory to reduce the safe connection ceiling by
50k. Hubs are therefore a latency/throughput trade-off, not a free win.


## Final compaction

Two more per-connection reductions landed:

- `connRooms` stores `*roomEntry` pointers instead of room-name strings. This
  removes one string header plus backing string per membership and avoids
  string comparison during Leave.
- `Accounting` fields were reordered so Go does not pad the struct from 32 to
  24 bytes.

At 500k this reduced server RSS from ~471 MiB to **431 MiB** and cgroup peak
from 1.22 GiB to **1.18 GiB**. The 4-hub safe ceiling remains **800k**; 850k is
still OOM-sensitive at 2 GiB.
