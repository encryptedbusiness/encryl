# 1 CPU / 1 GiB room benchmark

Date: 2026-10-25
Commit: working tree on `v2`
Host: `lima-encryl-dev`, Apple Silicon, VM 8 vCPU / 15.6 GiB
Kernel: 6.8.0-147-generic
Memory: VM memory 15.6 GiB; server capped with cgroup `MemoryMax=1G`, `CPUQuota=100%`
Go: 1.27.2 linux/arm64
Command: `bench/workload -role server -workload group -room-size 100 -loops 1` under `systemd-run`; client `bench/workload -role client`
TLS mode: plaintext `ws://`
Raw: console output in this report

## Purpose

Measure 500,000 connections with 100-member rooms on one CPU and a one-gigabyte
server memory limit. Record p95, p99, p99.9, and p99.99. Find the failure point
and distinguish application memory from kernel socket memory.

## Results

### 500k idle, 1 CPU / 1 GiB

The server reached 500,000 idle connections without OOM. Cgroup peak was
1,037,598,720 bytes (about 989 MiB). The run reported 5,986
`BufferExhausted` events during the ramp and no protocol errors. This is the
memory ceiling before any room metadata.

## Why it broke

Linux keeps a `struct tcp_sock` and socket slab allocation per TCP connection.
The slab accounting at 100k connections shows the fixed kernel cost directly:

| Slab cache | Active objects | Object size | Active size |
| ---------- | -------------: | ----------: | ----------: |
| `TCP` | 100,208 | 2.31 KiB | ~231 MiB |
| `sock_inode_cache` | 100,838 | 0.81 KiB | ~82 MiB |
| `filp` | 101,725 | 0.25 KiB | ~25 MiB |
| `io_kiocb` | 101,592 | 0.25 KiB | ~25 MiB |

Those entries alone are about **3.6 KiB per connection**. At 500k, `TCP` alone
is roughly **1.15 GiB** before the application heap. The Go side was about
**1.0 KiB per connection** in this workload. One gigabyte cannot hold both 500k
live TCP sockets and room metadata.

`accept_direct` is not a fix for this: it avoids creating a normal file
descriptor and fixed-file-table installation, but the kernel still allocates
the TCP socket, `struct file`, inode, and io_uring operation objects. It can
reduce fd bookkeeping and syscalls, not the `TCP` slab object.

`MaxConnections` and the Go slab are not the limiting factor. The cgroup OOM
killer is triggered by kernel socket memory plus application heap.

## Changes made from this run

- `room.Directory` now uses a compact per-connection slice instead of one map
  per connection. The heap category fell from **17.0 MiB to 10.0 MiB** per
  100k memberships.
- Production `room.NewSized` uses a lazily allocated dense per-slot membership
  table, so an idle server without rooms does not pay the table cost.
- Room names are canonicalized to one string per room.
- `bench/workload` reports p99.9 and p99.99 and accepts `-loops`.
- The benchmark server no longer reserves 2x the requested connection ceiling.
- `bench/workload` supports a heap profile on `SIGUSR2`.

## Next decision

Do not add hubs yet. Hubs shard room lookup, not socket memory, and would add
metadata. The 1-GiB ceiling must be addressed first: either lower the target to
the measured safe connection count, raise the memory budget to at least
~1.5-2 GiB for 500k, or change the transport/connection model. A hub benchmark
after that should use the same command and report p99.99 and OOM status.

The 100k / 100-member run is stable at 1 GiB. The 500k room-membership run was
still OOM-killed at 1 GiB after the compact and dense membership changes; the
remaining cost is kernel socket memory, not the room map. A 300k run used
763 MiB cgroup memory, of which 460 MiB was kernel/slab. This makes 500k live
TCP sockets plus room metadata a >1-GiB target on this kernel.


## Transport/connection options

| Option | Removes TCP slab? | Cost |
| ------ | ----------------- | ---- |
| `accept_direct` + fixed files | No; removes normal fd/file-table step only | Medium implementation; small memory win |
| Multishot accept / recv | No; removes repeat SQEs and some io_kiocb churn | Medium; latency win |
| `SO_RCVBUF`/`SO_SNDBUF` tuning | No; affects data buffers, not `tcp_sock` | Small |
| `tcp_mem` / cgroup tuning | No; accounting/reclaim only | Operational |
| Fewer TCP sockets / multiplexed logical clients | Yes | Protocol/API change |
| AF_XDP or user-space TCP | Yes, replaces kernel TCP | Very large implementation |
| Raise memory budget | N/A | 1.5-2 GiB for 500k rooms |

The only way to keep 500k *live TCP sockets* under 1 GiB is to change what a
connection is, not to tune a socket option. The hub work should wait until the
connection budget is chosen.


## 500k fan-out with tcpkali readers

The Go client was replaced with tcpkali for density. The server ran with one
loop and a 2-GiB cgroup because the 1-GiB cgroup still OOM-killed at 500k
room memberships. This run measures **server-side latency** from `Emit` to the
last socket write completion.

Command shape:

```sh
# server: 500k max, 5000 rooms, 100 members each, one loop
/tmp/encryl-fanout -addr 127.0.0.1:18092 -max-conns 500000 \
  -rooms 5000 -room-size 100 -loops 1 -count 1000 -interval 10ms -auto-start=false

# client: tcpkali, no 500k goroutine client
tcpkali --ws -c 500000 --connect-rate 10000 -T 90 ...
```

| Metric | Value |
| ------ | ----- |
| Connections open | 500,000 |
| Rooms | 5,000 |
| Members per room | 100 |
| Broadcasts | 1,000 |
| Messages out | 100,000 |
| p50 | 2.182 ms |
| p95 | 2.344 ms |
| p99 | 3.239 ms |
| p99.9 | 4.975 ms |
| p99.99 | 4.975 ms |
| Max | 5.367 ms |
| Process RSS | 437 MiB |
| cgroup peak | 1.19 GiB (2-GiB cap) |
| Protocol / file-table / recv / send errors | 0 / 0 / 0 / 0 |
| Accept errors during ramp | 15 |

This is the useful 500k result: the client no longer dominates memory, and the
server tail is milliseconds, not seconds. The remaining gap to the 1-GiB
target is kernel socket memory; a 1-GiB cgroup OOM-kills the same server.
