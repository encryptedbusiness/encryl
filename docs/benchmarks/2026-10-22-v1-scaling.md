Four runs of the same workload at increasing connection counts, on the host
below. The canonical per-run report is
`2026-10-22-v1-baseline.md` (200k); the other runs are preserved as
`-20k`, `-50k`, and `-100k` for the trend.

## Results

Load: idle connections (`loadgen -mode=idle`), each sending a WebSocket ping
every 30 s. No messages, no TLS. v1 example server with `GOMAXPROCS=1`.

| Target | Peak active | Failed | Server RSS peak | Process RSS / conn | TCP slab objects | TCP slab / conn |
| ------ | ----------- | ------ | --------------- | ------------------ | ---------------- | --------------- |
| 20k | 18,593 | 0 | 163.44 MiB | 9.00 KiB | 18,005 | 2.29 KiB |
| 50k | 50,000 | 0 | 430.11 MiB | 8.81 KiB | 50,037 | 2.37 KiB |
| 100k | 100,000 | 0 | 924.63 MiB | 9.47 KiB | 100,022 | 2.37 KiB |
| 200k | 200,000 | 0 | 1751.39 MiB | 8.97 KiB | 200,015 | 2.37 KiB |

TCP slab object size is 2368 B (`/proc/slabinfo`). Process RSS per connection is
flat at ~9 KiB, and kernel slab is flat at ~2.37 KiB, so v1's idle cost is
linear at roughly **11.3 KiB per connection** (WS, no TLS).

`sockstat` `mem` per connection is not used as the headline: it is a global
page-accounting snapshot that drifts with teardown (it reports 3602 B at 20k and
912 B at 200k). The slab object count is the stable measure.

## Reproduction

```bash
make limactl-up
make linux-shell
sudo modprobe tls
CONNS=200000 DURATION=12s RATE=60000 SRC_IPS=16 ./scripts/bench-baseline.sh
```

`SRC_IPS` spreads the generator over `127.0.0.2..N` to avoid ephemeral-port
exhaustion. The server is v1's `example/chat_server`, which hardcodes `:8080`.

## Comparison with the historical README claim

The v1 README claimed **201,624 connections at 1676.64 MB**, which is
**8.51 KiB per connection**. This run reaches **200,000 at 1751.39 MiB
(8.97 KiB/conn)** on a 4-vCPU VM.

The historical order of magnitude is therefore plausible; what was missing was
a command, a host, a kernel, and raw data. The claim is no longer used as
evidence and this file replaces it.

## What this does not measure

- **No message traffic.** Echo/unicast throughput is not comparable between v1
  and v2 without a protocol adapter (v1 JSON envelope vs v2 binary envelope).
- **No TLS.** v1 has none. The WSS budget in ADR-0002 is a different regime.
- **No long soak.** 10–20 s per run; no 60-minute hold, no post-stabilization
  growth check.
- **One host.** The 1M gates in `docs/roadmap.md` M3 are not addressed.

## Why this matters for v2

v1 uses ~9 KiB of process RSS per idle WebSocket connection and ~2.4 KiB of
kernel slab. v2's hypothesis is ≤1 KiB process RSS for plaintext and ≤4 KiB for
WSS. At 1M connections, v1's model needs ~9 GiB of process memory before TLS;
that is the gap the v2 architecture is meant to close, and the number the M1
epoll backend must be compared against.
