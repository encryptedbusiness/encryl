# HTTP 1 vCPU / 2 GiB benchmark

Date: 2026-10-25
Commit: working tree on `v2`
Host: `lima-encryl-dev`, Apple Silicon, VM 8 vCPU / 15.6 GiB
Kernel: 6.8.0-147-generic
Memory budget: server cgroup `MemoryMax=2G`, `CPUQuota=100%`
Go: 1.27.2 linux/arm64
Client: wrk 4 threads for throughput; oha 128 connections for p99.99
Command: see each section
TLS mode: plaintext HTTP
Raw: console output in this report

This is a FrameworkBenchmarks-shaped JSON/Plaintext run, reproduced locally
because the TFB Docker runner is not available in this VM. It uses the same
routes, keep-alive behavior, payloads, and 16/128/512 concurrency levels.

## Environment

- Ubuntu 24.04 / kernel 6.8 / arm64 / Go 1.27.2 in Lima on Apple Silicon.
- Each server runs in its own systemd cgroup:
  `CPUQuota=100%`, `MemoryMax=2G`, `MemorySwapMax=0`, `GOMAXPROCS=1`.
- Client: `wrk` 4 threads for throughput; `oha` 128 connections for the
  server-bound p99.99 run. Client and server are on the same host, loopback.
- JSON response: `{"message":"Hello, World!"}` (27 B), with `Server` and
  `Content-Type` headers.
- Plaintext response: `Hello, World!` (13 B).

## Results

| Transport | c16 req/s | c128 req/s | c512 req/s | c128 p50 | c128 p99 | c128 p99.99 |
|---|---:|---:|---:|---:|---:|---:|
| Fiber v3 / fasthttp | 258,728 | 269,777 | 252,821 | 0.471 ms | 1.02 ms | **1.38 ms** |
| standard net/http | 142,828 | 142,473 | 131,965 | 0.91 ms | 2.15 ms | 7.91 ms |
| httpuring + net/http | 27,864 | 67,325 | 132,418 | 1.88 ms | 3.03 ms | 6.71 ms |
| httpuring + fasthttp | 40,265 | 104,838 | 195,860 | 1.20 ms | 1.74 ms | 8.50 ms |
| httpuring raw HTTP/1.1 loop | 242,955 | **396,080** | — | **0.275 ms** | 5.99 ms | 7.61 ms |
| chi on httpuring, inline | 194,107 | 337,196 | — | 0.34 ms | 3.53 ms | 8.40 ms |
| chi on httpuring, 1 ring worker | 55,288 | 220,699 | — | 0.54 ms | 1.01 ms | 14.95 ms |

### Plaintext `/plaintext`

| Transport | c16 req/s | c128 req/s | c512 req/s | c128 p50 | c128 p99 |
|---|---:|---:|---:|---:|---:|
| Fiber v3 / fasthttp | **260,886** | **270,815** | **254,075** | 0.467 ms | 1.02 ms |
| standard net/http | 141,366 | 143,001 | 130,430 | 0.91 ms | 2.00 ms |
| httpuring + net/http | 28,621 | 66,910 | 131,479 | 1.90 ms | 3.06 ms |
| httpuring + fasthttp | 40,377 | 105,174 | 201,330 | 1.21 ms | 1.55 ms |
| httpuring raw HTTP/1.1 loop | 345,418 | **466,199** | **471,455** | **0.26 ms** | 5.50 ms |

The p99.99 column is the `oha` c128 run. After switching accepted sockets to
nonblocking poll-driven recv and batching accepts, raw p99.99 improved from
~11.5 ms to **7.61 ms** at c128. Server-side timing shows the remaining tail
is queueing inside the single event loop (p50 ~200 µs), not a stuck handler.
At c16 raw p99.99 is ~3.66 ms. Fiber remains the rare-tail winner because its
goroutine scheduler prevents one event loop from head-of-line blocking every
connection.

`Loops > 1` uses `SO_REUSEPORT`, but on this 1-vCPU cgroup it worsened both
throughput and tail because multiple locked loops contend for one CPU. Keep one
loop per vCPU.

## JSON serialization

The JSON handler uses a generated-style easyjson writer into a stack buffer:

| Encoder | ns/op | B/op | allocs/op |
|---|---:|---:|---:|
| `encoding/json.Marshal` | 104.4 | 64 | 3 |
| `goccy/go-json.Marshal` | 41.4 | 48 | 2 |
| custom easyjson writer, stack buffer | **12.8** | **0** | **0** |

The custom writer is not the benchmark bottleneck. JSON allocation is already
removed; the remaining gap is the HTTP/transport path.

## What this means

At one vCPU, a tuned Fiber/fasthttp JSON server is expected around
**270k req/s** at c128 and **250k req/s** at c512 on this host. Standard
`net/http` is around **132–143k**. The `httpuring` net/http bridge reaches
**67k at c128** and **132k at c512**; it is latency-bound at low concurrency
and catches standard net/http only once enough requests are in flight.
fasthttp over `httpuring` reaches **105k at c128** and **196k at c512**.

The raw `httpuring` HTTP/1.1 loop removes the net.Conn bridge entirely and
reaches **396k at c128**, with zero request-path allocations.
It beats Fiber on throughput and p50, but its single event loop has a worse
p99.99 under high concurrency than Fiber's scheduler. JSON is not the
blocker; the remaining tradeoff is raw throughput versus rare-tail fairness.

The ring-native `http.Handler` adapter keeps chi semantics. Running chi inline
reaches **358k at c128**; chi plus the BasicAuth route works unchanged. A
single request/response worker ring is slower for tiny JSON handlers
(**221k**) but improves p99 at c128; it is intended for handlers that block,
not for the zero-allocation path. The general recommendation is:

- raw `httpuring.Mux` for maximum throughput on static routes
- chi inline for normal API routing
- worker ring when handlers block
- `net/http`/chi on `httpuring.Listen` only for compatibility
