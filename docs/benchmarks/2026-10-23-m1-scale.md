The connection-density result is clean. The 1M message result is not yet clean:
M1 has one in-flight send per connection. A fixed-rate client that batches
messages per connection makes the first echo active and drops the rest. The
10k and 64.5k request/response runs, which read each echo before sending again,
show exact in/out parity and zero errors. That isolates the remaining defect to
the write path, not the parser, dispatch, or framing.

## Tool choice

### Existing tools evaluated

| Tool | Fit | Verdict |
| ---- | --- | ------- |
| **tcpkali 1.2.0** | C/libev TCP and RFC 6455 load generator; opens millions of connections using source-IP aliases; `-H` adds the required `Sec-WebSocket-Protocol` header; `\{ws.binary <file>}` sends a binary frame; `--source-ip`, `--connect-rate`, `-c`, `-T`, `-r` | **Used for 1M density.** Low client memory (~1.3 KiB/connection idle). | **Tsung 1.7.0** | Erlang, distributed, multi-protocol; Appwrite used 16 clients to reach 1M WebSocket connections; `ts_websocket` sessions and `maxusers` per client | **Viable fallback for distributed 1M messages.** Not used here because the single VM reached 1M with two tcpkali shards. | **k6** | JavaScript WebSocket load tests, binary messages, custom headers, distributed k6/operator | Good for scripted request/response and CI. One VU/connection and a goroutine-like runtime; 1M needs a distributed fleet, not a local single-VM run. |
| **bombardier** | Go HTTP(S) benchmarker built on fasthttp | **Not usable**: HTTP only, no WebSocket. |

### Why tcpkali was the right existing tool

`tcpkali` already implements the hard parts for density:

- Millions of connections from one host by spreading over source IPs.
- A real WebSocket handshake with custom headers.
- Binary frames from a file, so the 20-byte `encryl.v2` EVENT envelope can
  be sent without writing a custom client.
- Per-connection message rates and connection ramps.

It does **not** implement the server's request/response contract. Its fixed-rate
mode is a sender; per-connection batching can put several messages behind the
server's single in-flight send. The observed `SendBusy` counts are that client
shape meeting the M1 one-slot write path.

### tcpkali build

The original `machinezone/tcpkali` repository is no longer reachable from the
VM. The preserved public fork used was:

```bash
git clone --depth 1 https://github.com/MumiaiGene/tcpkali /tmp/tcpkali
```

Ubuntu 24.04 dependencies:

```bash
sudo apt-get install -y git build-essential autoconf automake libtool \
  pkg-config libssl-dev bison flex
```

The fork has one Linux portability bug: `src/tcpkali_syslimits.c` includes
`<sys/sysctl.h>` unconditionally. On Linux, guard it:

```c
#ifndef __linux__
#include <sys/sysctl.h>
#endif
```

Then:

```bash
cd /tmp/tcpkali
autoreconf -iv
./configure
make -j8
/tmp/tcpkali/src/tcpkali --version   # tcpkali version 1.2.0 (libev, ssl)
```

`/tmp` is cleared when the Lima VM is restarted; the binary, not the apt
packages, must be rebuilt.

### tcpkali gotchas found

- `--latency-marker` allocates an **HdrHistogram of 90,216 bytes per
  connection**. At 50k connections that is ~4.5 GiB; at 1M it is impossible.
  Never enable it for density runs.
- `-r 0.01` produced **zero** messages in the 1M run. Use `0.05` or `0.1` for a
  fractional per-connection rate.
- A single tcpkali process with `-c 1000000` stalled at **718,072** open
  connections. The server had 718,072 open, 0 errors, and 9.1 GiB still
  available; `ss -s` showed 1,436,497 established sockets, i.e. both sides of
  the 718k connections. The client, not the server, was the limit. Two shards
  of 500k each with disjoint source IPs reached 1M.
- The single-process `-T 300s` run had not exited after 611 s; it was still
  ramping. The sharded script kills the shards after its monitor window.
- The tcpkali final `Total data sent` counter is not a reliable connection
  count at large `-c`; use the server's `Stats` and the shard "Ramped up to N
  connections" lines.
- `pkill -f /tmp/encryl-echo` matches the wrapper shell's own command line and
  kills the test. Use `pkill -x encryl-echo`.

The normal M1 VM is 4 vCPU / 7.7 GiB. The scale run used a temporary override:


### Scripts

`scripts/scale.sh` — one tcpkali client:

- tunes the kernel sysctls;
- starts the echo server;
- creates `/tmp/encryl-msg.bin` with the 20-byte envelope;
- samples server RSS, tcpkali RSS, and `MemAvailable` every second;
- sends `SIGUSR2` five seconds before the end;
- prints peak/delta memory and the tcpkali/server result lines.

`scripts/scale-sharded.sh` — N tcpkali clients:

- splits `CONNS` into `SHARDS`, each with a disjoint `--source-ip` range;
- tunes the same sysctls, with `TCP_MEM` and `CONNTRACK_MAX` overridable;
- starts the server with `-max-conns`, `-tx-bytes`, `-buffer-count`,
  `-read-buffer`;
- sends `SIGHUP` to the server every `SAMPLE` seconds and prints the `Stats`
  line plus `free -m`;
- creates the envelope message file when `MSG_RATE` is non-zero.

### 20-byte message envelope

```text
02 02 00 00              version=2, kind=EVENT (2), flags=0
00 00 04 00              event=1024
00 00 00 00 00 00 00 00  request_id=0
50 49 4e 47              payload "PING"
```

tcpkali command fragment:

```bash
-H "Sec-WebSocket-Protocol: encryl.v2" \
-e -m '\{ws.binary </tmp/encryl-msg.bin>}' -r "$MSG_RATE"
```

The `-e` flag is required for the expression to take effect in the tested
build.

### Why this is not yet "correct at 1M with messages"

M1 admits **one in-flight send per connection**. The public path is:

1. recv may contain several complete WebSocket messages;
2. the handler calls `Conn.Send` for each;
3. the command ring admits each send command;
4. the loop drains commands and calls `sendFrame`;
5. the first frame takes the send slot; while it is active, the next
   `sendFrame` returns false, increments `SendBusy`, and drops the frame.

`Conn.Send` has already returned nil when the command was admitted, so the
caller cannot see the drop. That violates the explicit-failure commitment. The
counters make it visible in `Stats`, but a counter is not a delivery guarantee.

The fixed-rate tcpkali shape creates exactly this pattern: it sends messages in
per-connection batches and does not provide request/response backpressure.
The 10k and 64.5k Go runs, which read each echo before sending again, show that
the parser, envelope dispatch, handler, framing, and send completion are clean
when the client respects one in-flight.

## Defects found and fixed during this work

### 1. eventfd wake used `IORING_OP_READ`, which returns EOPNOTSUPP

The cross-loop wakeup armed `IORING_OP_READ` on an eventfd. On kernel 6.8 the
completion was `-EOPNOTSUPP` (95), not a successful 8-byte read. Each command
wake produced an error CQE and immediately re-armed, creating an error storm.

Observed in a 5k-connection, 1 msg/s-per-connection test:

```text
MessagesIn:66382
MessagesOut:45691
EventFDErrors:62560
EventFDErrno:95
SendBusy:20691
```

A pipe was tried first; `IORING_OP_READ` on the pipe also returned
EOPNOTSUPP. The final fix is:

- create a non-blocking CLOEXEC eventfd;
- arm `IORING_OP_POLL_ADD` with `POLLIN` on it;
- on the poll completion, drain the eventfd with ordinary `unix.Read` until
  `EAGAIN`;
- re-arm the poll.

After the fix the same shape reported `EventFDErrors:0`, `EventFDErrno:0`.
This is a real correctness/performance fix and should be kept.

### 2. `MessagesOut` counted attempted sends, not admitted frames

The counter was incremented before checking the send slot. It now increments
only after a TX block is taken or a heap buffer is allocated and the frame is
about to be submitted. This makes in/out comparisons meaningful and separated
the send-busy drops from parser losses.

### 3. Diagnostic counters were aggregated into one opaque `ProtocolErrors`

`Stats` now exposes:

- `RecvErrors`
- `SendErrors`
- `IllegalTransitions`
- `CQOverflow`
- `BufferExhausted`
- `EventFDErrors`
- `EventFDErrno`
- `SendBusy`

`ProtocolErrors` remains the sum of recv + send + illegal transitions. The
1M message investigation would not have been possible without the breakdown.

### 4. Fixed per-loop capacities were too small for 1M

| Setting | Before | After | Effect at 1M |
| ------- | -----: | ----: | ------------ |
| Ring entries | 8,192 | 32,768 | CQ overflow 62,686 -> 678 |
| CQEs per pass | 256 | 2,048 | keeps the CQ drained |
| Command ring | 256 | 4,096 | command backpressure 86,964 -> 0 |
| RX buffers per loop | 4,096 | 32,768 (2 KiB each) | buffer-exhaustion arms 16.2M -> 513k |
| Message buffer pool | 1,024 | 8,192 | fewer allocations under concurrent sends |
| Timer-wheel growth chunk | 512 | 4,096 | fewer node-slice copies during the 1M ramp |

These are scale settings, not universal defaults. The 32k-entry ring costs a
few MiB per loop; the 32k x 2 KiB RX arena is 64 MiB per loop (512 MiB at 8
loops) and is only justified for high-connection, high-message shapes.

### 5. tcpkali fork Linux build fix

As above: guard `<sys/sysctl.h>` with `#ifndef __linux__`. Without it the build
fails on `src/tcpkali_syslimits.c`.

### 6. tcpkali latency-marker memory

`--latency-marker` allocates 90,216 bytes per connection. At 50k it used 4.5
GiB; at 1M it is not viable. The scale runner does not enable it by default.

### 7. `MSG_RATE=0.01` sends nothing

Fractional rates below the tested values rounded to zero messages. Use 0.05 or
0.1 per connection.

## M1 gap: the per-connection write queue is missing

The roadmap's M1 deliverables include:

> Bounded per-connection write queues with `Reject`, `DropNewest`, `DropOldest`,
> and `CloseSlowConsumer`; `Send` reports admission synchronously. Encode-once,
> refcounted fan-out.

The measured M1 path does **not** have this. It has:

- a command ring for cross-loop admission;
- a single in-flight send per connection (`SendBid` or `extra.sendBuf`);
- `sendFrame` returning false and incrementing `SendBusy` when the slot is
  busy;
- `Conn.Send` returning nil once the command is admitted, before the loop
  discovers the busy slot.

The 1M message test is the first workload that makes this visible. The correct
next change is a bounded per-connection queue:

- queue built frames, not borrowed RX payloads;
- bound by messages and bytes;
- apply the configured policy when full;
- make `Conn.Send` admission atomic with respect to the send slot, so a full
  queue returns `ErrBackpressure` instead of a later silent drop;
- drain the queue from `handleSend` after each completed or partial send;
- keep the TX arena/owner checks and release every queued block exactly once.

Until that lands, the honest claim is:

- **1M idle connections: measured and clean.**
- **1M connections with messages: connection layer clean, message delivery not
  yet correct at the target rate; the one-slot send drops are counted.**
- **10k/64.5k request/response messages: exact parity and zero errors.**
